# Wallet conservation and compatibility

- The authoritative ledger stores exact nonnegative integers. Rewards, refunds, and team merges are not bounded by signed 32-bit arithmetic. `getExactCount` exposes the exact total; existing `getCount`, GUI, and network fields remain capped at `Integer.MAX_VALUE`. Spending or withdrawing repeatedly reveals and consumes all excess funds rather than discarding them.
- Physical deposits retain the prior signed-int headroom limit. Only accepted coins leave input slots; ME requests are bounded before extraction. Once ME extraction has committed, exact credit must preserve its returned receipt even if another credit has filled the visible balance.
- Ordinary saves retain their legacy integer fields. Overflow adds `__gtit_wallet_version=1` and decimal values in `__gtit_exact_balances_v1`; the old integer field is only a capped compatibility projection. **Do not downgrade a world containing overflow balances to an older GTIT version:** older writers do not preserve the exact side compound. Back up worlds before version changes.
- The exact **compound**, not a matching numeric key name, distinguishes the new format. Old integer balances named `__gtit_wallet_version` or `__gtit_exact_balances_v1` remain currency and migrate without loss. An actual exact compound still requires the supported integer version and consistent balances.
- Team merges drain the source exactly once. Old wallet references forward subsequent reads, debits, and refunds to the survivor; the consumed source serializes an empty ledger. Member transfers do not take funds from the previous team.
- Consumed team/history references also forward late trade completions, cooldowns, and notifications. Stale-target and chained merges route both money and redemption history to the same surviving owner; consumed data serialize neither money nor redemption counts twice. Member movement still copies history into an independent live team rather than aliasing it.
- Merges are serialized separately from ordinary wallet operations. Team callback locks precede wallet locks; wallet notifications only enqueue concurrent dirty keys, never acquire team locks. `transferAllTo` must not be called while holding a wallet monitor.
- History consume/copy merges use a separate merge gate and require callers not to hold history monitors. Full vending transactions and team callbacks remain server-thread operations; forwarding an old history reference does not turn its monitor into a transaction lock for the survivor.
- Joining a team freezes, but does not discard, the personal wallet. Saving or logging out also persists that frozen personal balance. A canonical personal ledger remains cached until a successfully saved world stop so late refunds cannot land in an evicted duplicate; the cache holds only UUIDs/balances, not players or worlds. Memory grows with distinct participants per world session.
- Wallet storage is unavailable until its world directory is initialized. A failed shutdown save retains its old-directory binding, disables wallet lookups, and must be saved successfully before any new world can bind. Continuing after an initialization error cannot serve or overwrite a previous world's balances. After fixing storage, reload the world to retry initialization.
- Saves hold the wallet lock through the file replacement and dirty-mark clearing. This favors correctness over I/O latency. Replacement uses a same-directory temporary NBT file and atomic move; unsupported atomic replacement or write failures preserve the existing file and pending dirty state. Invalid existing wallet files fail closed and are not silently replaced with zero balances.

## Limits

These changes are not a cross-file transaction log. Abrupt process termination can still lose changes since the existing periodic save, and permanent disk failures cannot guarantee durability; shutdown reports and retains remaining unsaved wallets while the process remains alive. Team persistence is still provided by GTNHLib. External ME extraction that throws after an undocumented partial mutation cannot be reconstructed without an extraction receipt. The native GUI/network protocol displays only the capped balance, not a formatted arbitrary-precision number.

Regression entry points: `WalletConservationTest`, `WalletManagerPersistenceTest`, and the existing `WalletCreditCapacityTest`, all invoked from `VendingConcurrencyTest`. Native team/lifecycle probes cover frozen-personal saving and retained logout identity. Lightweight fixture execution does not replace full Forge/GTNHLib runtime validation.
