## 修复计划（v1.7.36）

### 问题 1：抽奖界面钱包余额不实时

**根因**：抽奖界面的余额显示走 `LotteryClientData.getBalance()` 静态缓存，这个缓存只在收到 `LotterySyncPacket`（全量同步包，含卡池摘要 + 保底计数 + **钱包余额**）时才刷新。但 `LotteryRequestPacket.processLottery()` 在抽奖成功路径（line 126）只发 `LotteryResultPacket`（抽取结果驱动动画），余额/保底的刷新被推迟到延迟出货 `dispatchAll` 末尾（动画时长 + 150ms 后）才执行 `sendSyncToClient`。

因此：在动画播放期间（约数秒），客户端看到的仍是**抽奖前**的钱包余额——抽完但余额没变。贸易机界面走 `IntSyncValue` 实时同步所以不受影响，这是抽奖界面独立走静态缓存导致。

**修复**：在 `LotteryRequestPacket.processLottery()` 的抽奖成功路径（line 135，发 `LotteryResultPacket` 之后）立即发一次 `LotterySyncPacket`，让余额/保底即时更新。这样即使客户端在动画期间切看余额，数字已正确；延迟出货后的那次 `sendSyncToClient` 作为冗余刷新保留无害。

具体：在 `LotteryRequestPacket.java` 的 `processLottery()` 方法，`sendResultToClient(..., RESULT_SUCCESS)` 之后添加：
```java
LotteryNetworkManager.sendSyncToClient(player);
```

### 问题 2：保底充值重置条件错误

**根因**：`LotteryManager.drawSingle()`（line 350-354）用 `selected.getRarity().isAtLeast(LotteryRarity.RARE)` 判断是否清零保底计数——即**只要抽到 ≥RARE（非普通）就重置**。用户要求：只有抽到**保底品质**（`PityConfig.guaranteedRarity`，默认 EPIC）才重置。

**修复**：改用 `pity.getGuaranteedRarity()` 作为重置判定标准（line 350-356）：
```java
LotteryRarity guaranteedRarity = pity.getGuaranteedRarity();
boolean isHighRarity = selected.getRarity().isAtLeast(guaranteedRarity);
setPityCounter(teamKey, pool.getId(), isHighRarity ? 0 : currentCount + 1);
return new LotteryDrawResult(selected, isPity, isHighRarity, slotIndex, amount);
```
